## 项目是什么

《江湖夜雨》：单机、手机竖屏、全程点按操作的中文文字武侠游戏。目标是「武侠 MUD 里的 GTA」：世界大，做什么都行。

- 试玩网址：https://mud4u404.github.io/game006/ 。main 一更新，就自动部署到这里。
- 试玩预览：https://mud4u404.github.io/game006/preview/ 。维护者分支的最新构建，负责人合并 PR 之前先在这里玩。见下面「试玩预览」。

- 剧情文档：`docs/story.md`。第二节是只给设计者看的真相。
- 内容格式：`docs/content-guide.md`。
- 协作规则：`AGENTS.md`；审查和合并规则：`docs/auto-review.md`。

## 试玩预览（合并之前先玩）

负责人合并维护者的 PR 之前，只看截图不够，要能先玩一下。

- **网址**：https://mud4u404.github.io/game006/preview/ 。放的是维护者分支 `claude/determined-hawking-7fpvbg` 的最新构建；正式版（根目录）照旧是 main。
- **怎样更新**：维护者分支一推送，`.github/workflows/pages.yml` 就转到 main 上部署一次（`github-pages` 环境默认只许 main 部署），每次把 main 和维护者分支各构建一遍，一起放上去。两三分钟后刷新预览网址即可。部署排队、不互相打断；排在后面的那次总带着两边最新的代码。
- **存档和正式版分开**（`src/core/preview.ts`，`tests/preview.test.ts` 把关）。同一个网站的浏览器存储不分子目录，云存档也是同一个账号，预览版的新存档格式可能把正式存档改坏，所以预览页：
  - 本机存储的键全部换成 `jhyy-preview-` 开头（正式版是 `jhyy-`），存档、元数据、每日备份、读不出来的旧档都在这一套里，碰不到正式版的；
  - 不连云存档：不登录、不上传、不下载，登录入口换成一句「预览版不连云存档」；
  - 页面顶上一行「试玩预览：存档与正式版分开」。
  - 想用正式版的进度试新功能：正式版「人物 → 存档 → 导出存档码」，到预览版「导入存档码」。反过来不要做。
- **安全闸**：部署时在预览版的构建里找 `jhyy-preview-`，找不到（分支落后于 main，还没有这套隔离）就不放预览，只部署 main；预览版构建失败也一样。这时把最新的 main 合进维护者分支再推一次。
- **维护者开 PR 时**，在正文里写上预览网址和「怎样试玩验证」，例如：

  > 试玩预览：https://mud4u404.github.io/game006/preview/ （分支推送后两三分钟更新；存档与正式版分开，不连云存档）
  > 怎样验证：标题画面点「新的江湖」→ ……

- 维护者分支名写在 `pages.yml` 的 `PREVIEW_BRANCH` 和 `on.push.branches` 两处，换分支时两处一起改。

## 项目负责人的偏好（已经定下的事，不要再问）

- **界面**：D「素白卡片」风格。清爽，层级清楚。不让玩家输入指令，全部点按。
- **战斗**：即时回合制，加上见招拆招。应对方式按「以己之长」：从自己学会的武功里选，每种应对都有成算。成算由修为对比对手这一招的强弱算出来。**不要做靠找规律就能破解的机制。**
- **重复操作**：练功这类重复的事交给挂机和放置；主线可以不做。
- **规模**：在意体量，要的是 GTA 式的自由度。
- **活的江湖**（10-08）：江湖先于玩家存在，事情不等玩家，玩家凭心情去逛、去插手，不要用一条条任务推着玩家过关。写法见 `docs/huojianghu.md`。
- **有条件、有代价**（10-08）：极少有唾手可得的东西。武功都有前置，有的简单有的艰难；门派武功分入门和高深；学艺拿历练去换；帮手、特权、好东西都要付出点什么。
- **成本**：在意 token 用量。能交给机器检查的交给机器，能交给协作者写的交给协作者。
- **沟通**：
  - 用中文，不堆术语。
  - 操作类的说明要一步步写，写明点哪个按钮。
  - **能按原则定的自己定**（10-09）：设计取舍、数值、内容写法、界面细节，只要能按上面这些原则判断，维护者自己拍板、自己做，总结里写一句定了什么、依据哪条原则。只有原则之外、牵涉方向的事才问，问的时候用选项、标出推荐项。负责人原话：「这个你自己思考！原则我已经说过了！」「这种问题也是！」
- **文字**（10-09）：要求很高，金庸风格的中文武侠世界。
- **场景不拥挤**（10-09）：一个地点里不要齐刷刷站一堆人，「像派出所审犯人一样」，玩家不知道点谁；人多了就把地图铺开。
- **自我迭代**（10-09）：维护者要能自己找问题、自己改，常从资深文字 MUD 玩家、专业商业游戏开发者两个角度审，让游戏从业余走向成熟。 三个审查角色写在 `.claude/agents/`（老玩家、制作人、金庸文字编辑），多久请一次、结果怎么处理见 `docs/zishen.md`。

## 分工与流程

| 谁 | 做什么 |
|---|---|
| 维护者（Claude 主会话） | 设计、系统架构、数据格式、测试用例、CI。写「功能」Issue 时附上设计卡和测试用例 |
| 协作者（Trae 等，可以换） | 写内容；按测试用例实现功能。负责人发一次「读 AGENTS.md，进入自动模式」，它就一直用 `scripts/wait-for-work.mjs` 等任务，有新 Issue 两分钟内接走 |
| GitHub Actions | 检查每个 PR。只新增内容包的 PR，全部通过就自动合并，并自动部署 |
| 每日例行任务（Claude，用 Sonnet） | 北京时间每晚运行一次，照 `docs/auto-review.md` 执行：精修当天合并的内容、审功能 PR、补发任务 |
| 项目负责人 | 决定方向，给协作者发开工指令，合并功能 PR |

- 维护者自己的分支用 `claude/` 开头，改动都走 PR，由负责人合并。
- 每日例行任务在 claude.ai/code/routines 里叫「江湖夜雨 · 每日一审」。它唤醒一个挂好仓库的固定会话「江湖夜雨 · 每日一审（值班）」。每次运行的记录都写在 Issue #16「【记录】每日一审」下。
- **派活就是开 Issue**：打上「内容」或「功能」标签，协作者的 `wait-for-work` 两分钟内就会接走。有先后的任务在正文里写 `依赖：#编号`。不想让它马上做，就加「暂缓」标签。
- PR 合并后，CI 会按标题里的 `[#编号]` 关闭对应的 Issue。机器人合并时 GitHub 自己不会关，不关的话协作者会重复做。

## 工作流（10-08 自查后定的）

这两天的教训，和对应的做法：

| 教训 | 以后怎样做 |
|---|---|
| 顺序颠倒：先让协作者写满一百三十多门武功，拜师入口却没做，玩家一门都学不到；地图铺开了，连个看病的地方都没有 | **先地基、后上层**：一样东西先打通一条玩家点得到的最小闭环（一派、一个铺子），再批量派内容。顺序由维护者定，写在 `docs/ledger.md` 第四节，不把选择推给负责人 |
| 设计停在文档里：根基之眼、纸娃娃都只有设计卡 | **完成的定义**：玩家点得到 + 机器玩家走得到 + 维护者在浏览器里亲自走过一遍。总账里每一项写清「设计 / 样稿 / 已进游戏」 |
| 只有格式校验，没有「能不能玩」的检查 | 机器玩家（`tests/zoubian.test.ts`）进 CI：不报错、不卡死、任务都走得完。另有掏钱查钱、分支挡路、基础设施、拜师入门武功、根基之眼等检查。每查出一类问题，先问能不能做成机器检查 |
| 协作者质量「中」，同类问题反复出现 | **培训闭环**：`AGENTS.md` 第十一节「常见错误清单」，每日一审查出的新类型就补进去；协作者交活前对照清单，并跑 `ZOUBIAN_PREFIX=<前缀> npm run zoubian` 自查；同一条连犯两天，维护者把它做成 CI 检查 |
| 维护者一个人串行做，进度慢 | **助手并行**：系统级的活拆成互不打架的几条线，每条线交给一个在独立工作区（worktree）里的助手，各自跑全部检查后交回，由维护者合并、复跑机器玩家、在浏览器里走一遍。每条线约三十五到四十万 token，只用在系统级的活上；内容交给 zcode |
| 维护者的 PR 要负责人合并，一天好几次打扰 | 一个阶段攒成一个 PR：先开草稿挂着，做完转正。正文写清「怎样试玩验证」，附截图 |
| 协作者的任务依赖维护者的 PR 时，自动模式不等 | 已修：「依赖：#编号」写 PR 编号也会等它合并。依赖还没开出来的 PR 时，先挂「暂缓」 |
| zcode 的自动模式会断，要负责人重发指令 | 每日一审看协作者最近一次推送；超过一天没动静，在 Issue #16 当天评论的第一行提醒负责人重发开工指令 |

## 代码地图

```
src/core/     状态 S、存档（键 jhyy-save-v2；试玩预览换成 jhyy-preview- 开头，preview.ts）、时间、工具函数
src/content/  types.ts 数据格式；index.ts 合并内容包（自动补回程出口，按 at 放置人物）
              skills.ts 武功与境界；packs/*.ts 内容包，按文件自动收录
src/engine/   dsl.ts 条件与效果；world.ts 寻路、动作；formulas.ts「以己之长」成算；growth.ts 熟练度与突破
src/ui/       shell.ts 外壳与 hooks；explore/fight/story.ts；views/ 下是五个标签页
tests/        content.test.ts 内容校验；style-rules.ts 文风与剧透规则；engine.test.ts
scripts/smoke.mjs  冒烟测试（npm run smoke）
scripts/luandian.mjs  乱点测试（npm run luandian）：从「新的江湖」起随机点四百下，报错、卡死、白屏就失败；换种子 LUANDIAN_SEED=7，点几下 LUANDIAN_STEPS=1000
```

几个关键约定：
- **效果分两类**：
  - 一般效果在 `engine/dsl.ts` 的 `run()` 里执行。
  - 开打、开剧情这两种要界面接手。`run()` 只把它们记进 `Outcome`，由 `ui/shell.ts` 的 `afterOutcome` 处理，这样避免循环引用。
- **成算的算法**：
  - 火候 = 境界 × 10 + 对应的属性。
  - 成算 = 基数 + (火候 − 对手这一招的强度) × 0.025，结果限制在 5% 到 95% 之间。
  - 基数一般是 0.5，抢攻是 0.35。
- **改动之后**：
  - 改了数据格式，同时更新 `docs/content-guide.md` 和 `tests/content.test.ts`。
  - 加了能让机器检查的规则，写进 `tests/style-rules.ts`。
