# 质量体系

确保出品质量的几道关、测试分层、问题怎样修，以及 AI 试玩员。

## 一、四道关

| 关 | 谁 | 什么时候 | 看什么 |
|---|---|---|---|
| 1 机器检查 | GitHub Actions | 每个 PR | 类型检查、全部测试、打包、冒烟测试。只新增内容的 PR，全部通过后自动合并 |
| 2 每日审查 | 值班会话（Claude Sonnet） | 每晚 21:53 | 按 `docs/auto-review.md` 精修当天合并的内容；审功能 PR；**对照宪章逐条检查**；给协作者评级 |
| 3 试玩 | AI 试玩员 | 每个阶段收尾时，平时每周一次 | 真的去玩，写试玩报告：好不好玩、哪里困惑、哪里出戏、哪里卡住、哪里违反宪章 |
| 4 验收 | 项目负责人 | 每个阶段收尾时 | 看试玩报告，自己玩一玩，决定阶段是否算完成 |

## 二、测试分层

| 层 | 文件 | 守什么 |
|---|---|---|
| 规则 | `tests/engine.test.ts`、`tests/wuxue.test.ts` | 条件和效果、寻路、成算、品级与境界、克制、修为 |
| 内容 | `tests/content.test.ts` | 引用完整；出口能往返；有兜底分支；武功预算；剧透词；现代词；数字写法；出场人物不用书中人物的名字 |
| 端到端 | `scripts/smoke.mjs` | 从标题画面一路玩到首领战，页面不报错 |
| 节奏 | 待建，M3 | 模拟认真玩家，大约九十天成宗师，不会速成 |
| 平衡 | 试算台，以及将来的模拟战斗 | 武功之间没有一家独大 |

**每修一个问题，就补一个能重现它的测试**，以后不会再犯。

## 三、发现问题以后

1. 不管是谁发现的，都开一个 Issue：用「问题」模板，标题写成 `【问题】…`。
2. 小问题：每日审查顺手修掉，并补测试。
3. 大问题：由维护者判断，是马上修，还是排进 `docs/roadmap.md` 的某个阶段。
4. 违反宪章的问题，一律当作大问题处理。

## 四、AI 试玩员（M1 建设中）

**怎么玩**：
- `scripts/playtest/` 提供一个文字版的操作接口。它在无头浏览器里运行游戏，把当前画面转成文字（地点、描写、人物、按钮），再接收「点哪个按钮」的指令。
- 试玩员是一个定期唤醒的 Claude 会话，通过这个接口真的去玩。

**扮演谁**：每次扮演一种玩家，各有侧重：

| 玩家 | 关注什么 |
|---|---|
| 新手 | 上手是否顺畅，会不会迷路 |
| 金庸迷 | 文笔、武学、江湖味 |
| 挑剔的老 MUD 玩家 | 深度、自由度、重复感、数值 |
| 探险家 | 隐藏内容、谜题是否公平 |

**交什么**：一份试玩报告，开成 Issue，标题是 `【试玩】<日期> <扮演的玩家>`，内容包括：
- 一句话总评；
- 最好玩的三处、最糟的三处；
- 困惑、卡住、出戏的地方，并写清怎样重现；
- 宪章逐条打分，从一到五；
- 建议。

报告里发现的问题，再分别开成 `【问题】` Issue。

**什么时候玩**：每个阶段收尾时一次；平时每周一次。

## 五、每周优化审查（M1 建设中）

每周日，值班会话额外做一次全面体检，包括：
- 代码健康：重复代码、过长的函数、越来越乱的模块；
- 文档有没有和代码脱节；
- 打包体积和加载速度；
- 截图对照，检查界面风格是否统一。

挑出最值得做的三项改进，开成 Issue。
